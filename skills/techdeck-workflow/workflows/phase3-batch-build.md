# `workflows/phase3-batch-build.md`

# Phase 3: スライドのバッチ作成（既定）

## Purpose

承認済みの構成をもとに、**複数のスライドをまとめて作成する**。
作成した各スライドは、ユーザーに渡す前に build → review → fix のループを通す。

これが Phase 3 の新規作成の**既定の動作**である。1枚だけの作成は、
ユーザーが明示的に求めた場合のモード（`phase3-slide-creation.md`）。

## ループは承認を代行しない ─ 最初に読むこと

ループの合格基準は「未解決の `CRITICAL` / `HIGH` が 0」であり、これは
`phase4-deck-final-review.md` の最終化基準と同一のバーである。

**このバーを満たしたスライドの終端は `AWAITING_REVIEW` である。**
評価用エージェントが返す `PASS` はレビュー総合判定（`status-vocabulary.md` の名前空間(3)）
であって、スライド状態(1)の `APPROVED` ではない。両者は別の名前空間である。

**`APPROVED` へ至る経路は、ユーザーの明示的な指示ただ一つのままである。**

ループが上げるのは、ユーザーに届くスライドの下限であって、ユーザーの権限ではない。

## Preconditions

* `TASK.md` の Current phase が Phase 3 である
* `slides/outline.md` と `slides/storyboard.md` が承認済みである
* バッチ対象のスライドがすべて `NOT_STARTED` である
* `slides/deck.pptx` が存在する（無ければ `new_deck.py` で器を作ってから始める）

条件を満たさない場合は作成せず、理由を報告する。

### `review_state.md` の `## Rules` を確認する

**バッチ作業の最初の操作として**、対象プロジェクトの `slides/review_state.md` の
`## Rules` 節を読む。

「`AWAITING_REVIEW` または `REVISION_REQUIRED` のスライドがある間は、次のスライドを
作成しない」に相当する行があれば**旧版**である。バッチ作成と直接矛盾するため、
`reference/state-schema.md` の「既存プロジェクトの移行」に従って**置換を提案する**。

**黙って書き換えない。** ユーザーの承認を得てから置き換え、`notes/decisions.md` に DEC を立てる。

## Procedure

### 1. バッチを解決する

最初に一致したものを採用する。

| 条件 | バッチ |
| --- | --- |
| ユーザーが範囲を明示（「30〜43を作って」） | その集合 |
| ユーザーが章を指定（「Chapter 3 を作って」） | その章の `NOT_STARTED` スライド |
| 「続き」「次」または単に作成を依頼 | `outline.md` 上で `NOT_STARTED` を含む**次の章**のスライド |
| いずれも解決しない | **ユーザーに聞く。推測でバッチを決めない。** |

**対象は `NOT_STARTED` のスライドのみ。**
`AWAITING_REVIEW` / `REVISION_REQUIRED` / `APPROVED` のスライドは、
ユーザーの明示指示がない限りバッチに含めない。これが旧ブロッキング規則の代わりの保護である。

`slides/deck-profile.json` に `batch` キーがあればその設定を使う。無ければ既定値。

```json
"batch": { "unit": "chapter", "max_slides_per_wave": 8,
           "max_iterations": 3, "review_concurrency": 4,
           "max_chapter_slides": 12 }
```

章が `max_chapter_slides` を超えるときは、節ごとに分けたバッチを提案してから始める
（Phase 2 で分けていればそれに従う）。

### 2. 出典を確定する ─ 建てる前に、一次情報に当たり直す

バッチが引く `SRC-NNN` を storyboard の `### Sources` から集め、**1 枚も作る前に**次を行う。

1. 各 `SRC-NNN` の一次情報を**開き直す**（生 HTML・PDF 原本・ソースコード）。
2. storyboard が依拠する文言が `### Verbatim quotes` にあり、原文と一致することを確かめる。
   無ければ原文から取って索引に足す。索引にあって原文に無ければ索引を直し、
   その文に乗っている storyboard の主張を直す。
3. 画像 PDF は該当ページを描画し、段落を全部転記してから storyboard の文を確定する。
4. 否定の主張（「〜は規定が無い」）は範囲と確認日を `### Absence claims` に書く。
5. この章に関わる `OQ-NNN` が残っていれば先に解決する（解決できなければ、その主張を使う
   スライドは `BLOCKED` にして報告する）。

これは `grep` で索引に語があるかを見る確認（作る直前の最後の防壁）とは**別の、一段重い工程**
である。grep は索引の誤りを通す。索引に「ページに無い文」が逐語の顔で入り、キーメッセージが
それに乗った実例がある。

効果は実測済み: 建ててから出典を取り直した章は `CRITICAL` 1・`HIGH` 4、建てる前に固めた章は
`CRITICAL` 0・`HIGH` 0〜4 で、残った `HIGH` もほぼ「仕様をビルド後に直した」順序の問題だった。

索引を直したら、**仕様面をすべて掃く**（下記「仕様面」）。

### 3. `## Current target` にバッチを記録する

`reference/state-schema.md` のバッチ形式で `slides/review_state.md` に台帳を書く。
バッチIDは `bNNN`（連番）。対象スライドを `DRAFTING` にする。

**`slides/review_state.md` を書くのはオーケストレータ（このターン）だけである。**
どちらのエージェントにも書かせない。

### 4. 波0 ─ パイロット1枚

バッチの先頭1枚だけを、単独でループに通す。

```
build → render → review → fix → review
```

得られた `Carry forward: yes` の指摘を `## Feedback carried forward` に統合する
（足すときは `reference/state-schema.md` の「横断ルールを足すときの 4 点検」を通す）。

**なぜ先に1枚か:** 7枚を作ってからレビューすると、1枚目で分かった教訓が残り6枚に届かない。
先頭1枚でバッチ全体の作法を確立してから残りを作る。追加コストは COM セッション1回分。

**パイロットの成果物は「その 1 枚」ではなく「後続に渡す型」である。** 共有する図のモジュール、
カードの寸法、脚注箱の幅、出典行の位置 ─ 後続スライドが継ぐものをここで固める。型の穴
（後続の variant が必要とする差分を表現する口が無い、幅を決めていない）は、その 1 枚だけを
見ていても見つからない。パイロットのレビュー依頼には「後続 N 枚がこの型で何を変えるか」を
渡し、型として成立するかを見させる。放置すると次の枚で「規則を破る」か「保証を壊す」かの
二択になる。

バッチが3枚以下、または `## Feedback carried forward` が既に充実している場合は省略してよい。

### 5. 波1..n ─ 残りを `max_slides_per_wave` ずつ

各波で次を行う。

```
直列:  build × k                （deck.pptx は1ファイル。同時実行しない）
1回:   render_deck.py --slides 31-37 --png-dir <out>   （COMセッション1回にまとめる）
並列:  review × k               （≤ review_concurrency）
直列:  失敗したスライドだけ fix
1回:   修正したスライドだけ再render
並列:  修正したスライドだけ再review（差分モード）
```

反復は `max_iterations` まで。各波の終わりに `review_state.md` を更新する
（中断しても失うのは1波分になる）。

**レビュー記録（`slides/reviews/slide-NNN.md`）は反復のたびに、その場で追記する。**
バッチの最後にまとめて書かない。途中で会話が圧縮されると、過去の結果を会話記録から
掘り起こすことになる（実例あり）。

各 build 指示と各 review 指示には、
`python scripts/statekit.py show-cf slides/review_state.md --for-slide N --storyboard slides/storyboard.md`
の出力を渡す（規則 1 件 1 行。図・コードの無いスライドではそのタグの規則を省く。件数は先頭行で確認できる）。
**`## Feedback carried forward` の全文は渡さない** ─ 100 件・118KB になった実例で、全文を読んだ agent は
居なかった。整合パス（§6）だけは `show-cf` を無指定で全件渡す。
発注文の構成は下記「発注文の契約」「発注文の上限」に従う。

review 指示には `RUBRIC` に加えて **`VISUAL`**（`reference/visual-design.md` の絶対パス）
を渡す。R8 の数値はそこにしか無く、渡さないと評価用エージェントが閾値を発明する。

ビルダーの `BUILD RESULT` が返ったら、台帳を更新する前に次を確かめる。

* **「指定から外れた所」のうち意味を持つもの**（行のそろえ方・線の結び方・ラベルの位置・順序・
  まとまり）は、見た目だけのものと分けて報告されている。意味を持つものは、一次資料と PNG で
  確かめてから認める。行をそろえれば「この 2 つは対応する」という主張になる。
* **「数えなかったもの」の一覧**を `visual-design.md` §5 の表で確かめてから、字数をユーザーに伝える。
* 「出典が無いので描かずに報告」は正しい動作である。記憶で描かせない。索引に足すか、
  「規定なし」として帰属を書くかを決めて再発注する。

fix の反復で**オーケストレータが storyboard に文を書く**ときは、下記「指摘の反映」に従う。

### 6. バッチ整合パス

全スライドのレンダリング済み PNG を使い、評価用エージェントを `MODE: batch` で起動する。
ルーブリック R6（スライド間の整合）のみを見る。

**R6 の前に:**

* 各スライドのレビュー記録の `### R6 notes` と、横断ルール追加時の全文検索で積んだ波及を
  集めて渡す。1 枚ずつのレビューでは見つからない不整合（赤い破線枠の意味が 2 枚で違う、
  「労働者供給」と「労働者供給事業」の使い分け）を、ここが拾う。
* 「R6 で直す」と決めている直しは、R6 の**前に** storyboard に書いておく。R6 には、
  それが章とそろっているかだけを見せる。この順序で b003 の R6 は 1 回で終わった。

ここで、波の途中で追加された横断ルールが、それ以前に作ったスライドにも適用される。
`R6-8`（キーメッセージの体裁が全スライドで一致しているか）は、この整合パスでしか見つからない。

**完成済みスライドを新しい横断ルールのたびに再ループさせてはならない。**
それは発散する。既存スライドへの遡及適用は、全文検索で波及を列挙し、このパスでまとめて行う。

R6 の指摘を直列で fix し、再レンダリングし、**直したスライドだけを差分で再確認する。**
**未解決の `CRITICAL` / `HIGH` が 0 になるまで繰り返す。** 1 回で終わる前提にしない
（b002 は修正の回帰と後追いの横断ルール適用で 3 回まわった）。

### 7. 記録して確定する

* スライドごとの `slides/reviews/slide-NNN.md`（反復ごとに追記済み）を最終形にする
* `## Current review request` にバッチの節を追記する（新しいものを上に積む）
* 各スライドの状態を離脱条件に従って更新する
* **storyboard の節を畳み直す。** `AWAITING_REVIEW` になったスライドの節は「今の仕様 1 つ」にする。
  無効になった欄を消し、`### Current spec` を更新し、`### Spec changes` の履歴はレビュー記録へ移す。
  上書きの欄を新しい順に積み続けた storyboard は 13,000 行を超え、レビュー担当がほぼ毎回
  「古い記述」を指摘した。
* **`## Feedback carried forward` を統廃合する。** `deck-profile.json` の `conventions` に吸収できる
  規則を移し、CF では参照だけ残す。同じ対象（タグ）の規則どうしが矛盾していないか見る
  （`reference/state-schema.md`）。
* 承認済みスライドへの波及は `## Approved slide change requests` に `ASC-NNN` で積む。
  **承認済みスライドは触らない。**

## 離脱条件

| 条件 | 総合判定 | スライド状態 | 追加の処理 |
| --- | --- | --- | --- |
| 未解決の指摘が0件 | `PASS` | `AWAITING_REVIEW` | ─ |
| 未解決の `CRITICAL`/`HIGH` が0、`MEDIUM`/`LOW` が残る | `PASS_WITH_MINOR_FIXES` | `AWAITING_REVIEW` | 残りを `DEFERRED` にし理由を報告 |
| 反復上限に達し `HIGH` が残る | `REVISION_REQUIRED` | `AWAITING_REVIEW` ⚠ | 指摘を `Points to review` と storyboard の `### Known risks` に転記 |
| 反復上限に達し `CRITICAL` が残る | `REVISION_REQUIRED` | **`BLOCKED`** | 技術的に誤っていると分かっているスライドをユーザーのレビューに回さない |
| 残りの未解決指摘がすべて `Fixable by builder: no` | `REVISION_REQUIRED` | 上の重要度に従う | **反復を消費せず即離脱** |
| 評価用エージェントが2回続けて `BLOCKED` を返す | ─ | `BLOCKED` | ツール／指示の不具合として報告 |
| 上限に達して残った `HIGH` が、直前の反復で**オーケストレータが仕様に書いた文の誤り**によるもの | `REVISION_REQUIRED` | `AWAITING_REVIEW` ⚠ | その旨をユーザーに示し、**1 回の延長**を諮る。作成役とレビュー担当は正しく動いており、反復を消費したのはオーケストレータである |

**`MEDIUM` はゲートしない。** `check_deck.py` のキャンバス外判定とコントラスト判定は
`MEDIUM` で誤検出が多く、これをゲートにするとループが空回りする。

### 発振ガード

> 反復 N の未解決指摘の集合が、反復 N−1 と同一（同じ locus × 同じ category）の場合、
> 残り反復を消費せず**即座にループを抜ける**。

同じ指摘が2回続くのは実行の問題ではなく**仕様の問題**である。
レビュアーの指摘とビルダーの反論を**両方そのまま** `Points to review` に載せ、
ユーザーに判断を委ねる。

### 修正できない指摘の扱い

`templates/review-report.md` の `#### Required workflow` の値で振り分ける。

| Required workflow | 処理 |
| --- | --- |
| `phase1-research.md` | `notes/open_questions.md` に `OQ-NNN` を立て、スライドを `BLOCKED` にして報告 |
| `phase2-structure.md` | 分割・順序変更を提案（削除ではなく分割）して停止 |
| `phase3-slide-review.md` | ループを続ける（通常の修正可能ケース） |
| なし ＋ `NEEDS_USER` | `Points to review` に載せ、`AWAITING_REVIEW` にする |

## 仕様面 ─ 1 つ直したら全部を掃く

スライドの仕様は 1 箇所に無い。次の **5 つの面**に分かれて存在し、どれか 1 つを直して他を
放置すると、残った古い記述を根拠に再生成されて `HIGH` が再発する（陳腐化の実例 6 件）。

| # | 仕様面 | 陳腐化の典型 |
| --- | --- | --- |
| 1 | `slides/storyboard.md` の節 | 撤回した値が 24 行下の要約表に残る |
| 2 | `slides/review_state.md` の `## Rules` と `## Feedback carried forward` | 改訂した規則の旧文を消さず、同じ規則が 2 つの答えを持つ |
| 3 | **発注文**（ビルダー・レビュー担当への指示） | storyboard の `### Sources` を直した直後の発注文に古い番号を書く |
| 4 | `assets/diagrams/*.py` の docstring と引数 | 仕様を変えたのに生成器の既定値が古い |
| 5 | `sources/source_index.md` | 索引を直したのに、それに乗っていた storyboard の主張が古い |

**規律:**

* 面 1〜5 のどれかを直したら、同じ編集で他の 4 面を grep して掃く。「直した」という記憶が、
  同じ文書の別の場所を確認させなくする。
* 仕様を訂正するときは**本文を書き換える**。注記の追記で済ませない（「① 本文を書き換える
  ② その下に ⚠ を書く。① を省かない」）。
* 識別子・値を置換したら、それを参照している全行を同じ編集で確かめる（宣言側の `Home` を
  直さずに使用側だけ `ProductList` に変え、コンパイルの通らない断片を作った実例）。
* 一括編集スクリプトは**編集ごとに書き込み**、書いたら**置き場**まで検証する
  （`src003_line < block_line < src004_line`）。`grep -c` は存在を教えるが置き場を教えない。
  破棄が起きたら再実行ではなく「何を書くはずだったか」のリストから作り直す。
  記録の書き込みは `scripts/statekit.py` を使う（節境界・1 回一致・改行コードを機械が守る）。

## 発注文の契約

発注文は仕様面の 1 つであり、**最も陳腐化しやすい**（頭の中に古い版が残ったまま書く）。
さらに、レビュー担当への誤った転記は**捕まえる側を壊す**（未検証の逐語を渡し、実在しない文を
前提にした所見が組み上がった実例）。だから発注文は散文ではなく、次の**キーと値だけ**で書く。

### ビルダーへの発注

| キー | 値 |
| --- | --- |
| `PROJECT_ROOT` | 絶対パス |
| `MODE` | `BUILD` / `FIX` |
| `SLIDE` | デッキ位置とタイトル |
| `STORYBOARD` | `slides/storyboard.md` の絶対パスと `## Slide NNN` 見出し。**「`### Sources` と `### Current spec` に従うこと」**。「`statekit.py show-slide --slide NNN` で 1 回で読める」と添える |
| `SOURCES` | `sources/source_index.md` の絶対パス。**`SRC-NNN` の一覧も本文も転記しない** |
| `EXAMPLES` / `PROFILE` / `VISUAL` | 絶対パス |
| `CARRIED` | `show-cf --for-slide NNN` の出力（この節だけは本文を渡す。規則は命令形の一文で、転記しても陳腐化しにくい。**節の全文は渡さない**） |
| `PRIOR`（FIX のみ） | `slides/reviews/slide-NNN.md` の絶対パスと `## REVIEW RESULT`（反復 N−1）の見出し、PNG のパス。**ブロック全文は転記しない**（§5 のとおり記録は反復ごとに追記済み。無ければ先に `statekit.py review-append` で書く） |
| `PILOT_FOLLOWERS`（パイロットのみ） | 後続 N 枚がこの型で何を変えるか |
| `PROGRESS_FILE` | ビルダーが段階ごとの進み具合を書く scratch ファイルの絶対パス（API の上限で止まったときの再開点） |

### レビュー担当への発注

`agents/techdeck-slide-reviewer.md` の「What you are given」のキーをそのまま使う。
加えて次を守る。

* **出典の本文を一切書かない。** 「索引の `SRC-NNN` を読め」と観点だけを書く。
  ビルダーの報告から取った文を貼らない ─ 検証していない文は存在しないものとして扱う。
* **比較基準を指名する前に `review_state.md` の状態を確認する。** 未承認スライドを「承認済み」
  として渡すと、未承認の逸脱を正として固定する。
* **ビルダーの言い分を渡さない。** `PRIOR` にはビルダーの `Finding dispositions` 表（主張と根拠）
  を渡してよいが、それを「事実」として要約しない。
* 推奨文言を求める発注はしない。レビュー担当の文例は「直し方の一案」であり、採るときは
  下記「指摘の反映」を通す。

### 発注の前に

* storyboard を直した直後の発注は、**直した箇所を転記せず参照させる**。
* `CARRIED` の規則が `conventions` に吸収済みなら、`PROFILE` を読ませる。

### 発注文の上限

発注文は**契約の表＋`CARRIED`（`show-cf` の出力）＋観点の散文 5 行まで**。合計 80 行を超えたら、
超過分（確認した事実の列挙、R6 の候補、反復の進め方）は `slides/reviews/slide-NNN.md` に
`statekit.py review-append` で書き、発注文にはそのパスを書く。
出力は $50/MTok で払い、次の呼び出しで cache write としてもう一度払う
（実測: 発注文 1 本 11〜27KB、オーケストレータ 1 ターンの出力 33〜53K トークン）。
情報は落とさない ─ 置き場を変えるだけである。

---

## 指摘の反映 ─ オーケストレータが文を書くとき

レビューの指摘に答えて**オーケストレータが書き足す・書き換える文は、新しい内容である。**
Phase 1〜2 と同じ照合を通す。1 バッチで 7 件の `HIGH` が、急いで書いた直しの文から出た。

1. 文を書く前に、storyboard の `### Spec changes` に 1 件起こし、**6 点検**を埋める
   （一次資料 / 言い換え / オン・オフ / 新語 / 例との整合 / 実物を見た）。埋められない点検がある
   文は書かない。
2. **レビュー担当の推奨文言・文例をそのまま仕様に入れない。** 文例は検証済みの文言ではない
   （推奨どおり足した文に主語が無く、既存の横断ルールに反して次の反復で回帰になった実例。
   同じレビュー担当が iter2 でそれを `HIGH` と判定し直した実例）。6 点検と `CARRIED` に照らしてから採る。
3. **字数に収めるために詰めた文は、意味を変える修正として差分レビューに回す**
   （`reference/visual-design.md` §5）。
4. **実測を根拠にするときは、まず取り直して `SRC-NNN`（検証結果）に残す。** レビュー担当や
   作成役の実測だけを根拠にしない。出典に日付を入れてから storyboard に書く。
5. 「他のスライドに移した」「Slide NN を参照」と書くときは、`notes/decisions.md` の
   `### Relocation check` を埋める（移す先に**その語が実際にあるか**をデッキ全文検索で確かめ、
   主語・違反・役割まで同じかを PNG か原本で見る）。
6. 直しの文が多い反復では、ビルダーに出す前に、文だけを照合する軽いレビュー
   （レビュー担当の `MODE: spec`）を挟んでよい。`HIGH` を 1 件防げば 1 反復分の節約になる。
7. 書いたら「仕様面」の規律で他の面を掃く。

## 分割の判断 ─ 1 枚ずつ決めない

1 枚が入らないと分かった時点で、そのバッチ**全体**の余裕を見る。1 枚ずつ決めると、同じバッチの
中で番号の付け替えが 2 回、承認済みスライドの再承認が 2 回になる（実例: 9 枚と 8 枚）。

1. **試し組みで測る。** 字数の見積もりで「入る見込み」を判断しない。見積もり 505 字で例外を認め、
   作ったら 547 字・0.30in はみ出した実例がある。ビルダーに試し組み（trial build）を発注し、
   字数と in の実測を取る。
2. **バッチ全スライドの余裕を一覧にする**（`### Visual hierarchy` の余裕欄）。上限に近い枚を列挙する。
3. 上限に近い枚の**分割・付録への移動・列の統合をまとめて決める。** 付け替えは 1 回にする。
4. `scripts/renumber.py --insert-after N`（既定は dry run。`--apply` を付けるまで何も書かない）で
   変更一覧を出す。承認済みスライドに当たる箇所（ページ参照・章の地図・付録のページ列・CF の由来）と、
   書き換えなかった候補（`旧 NN`・`N枚目`・`p.N`）は別に列挙される。`p.N` をデッキのページ参照として
   使っている案件は `--pages` を付ける（`source_index.md` の `p.N` は PDF のページなので対象外）。
   デッキ本体の文字は `--scan-deck slides/deck.pptx` で一覧にし、ビルダーに直させる。
5. **ユーザーに一度に諮る。** 推奨案を先頭に置き、影響（再承認が要る枚数、番号の変わり方、字数）を添える。
   承認済みスライドについて「ページ番号だけを付け直す」許可もこのとき得る。
6. 承認後に `renumber.py … --apply` を実行し、`## Deck structure note` の「番号の振り直しの履歴」に
   対応表を `statekit.py` で追記する。承認済みスライドの再承認は「変わった文字の一覧」と
   「前後を並べた画像」で頼む。

## 実行環境

* **API の 529（Overloaded）が続くときは、数分あけて再送し、`review_concurrency` を下げる。**
  並行レビューが多いとまとめて落ちる（実例: 5 分待って再送で復帰）。
* **ビルダーには段階ごとの進み具合（保存した・描いた・確かめた）を `PROGRESS_FILE` に書かせる。**
  API の上限で途中で止まっても、再開の発注で「どこから」を指せる。
* ビルダーのビルドスクリプトには毎回同じ守りを入れさせる: 対象外の位置を拒む、枚数とタイトルを
  確かめる、一時ファイルから置き換える、対象外のスライドが XML まで同一かを確かめる。
  これがあると、途中で止まっても保存の状態が確かで、`SendMessage` で続きから終えられる。
* エージェントがプロセスを止めるときは自分が起こしたものだけ（PID 指定）。広い範囲の
  `taskkill` / `kill` は、直列で守っている build と render を別のエージェントが壊す。

## エージェントの役割分担

| | `techdeck-slide-builder` | `techdeck-slide-reviewer` |
| --- | --- | --- |
| tools | Read, Write, Edit, Glob, Grep, Bash | **Read, Glob, Grep, Bash のみ** |
| `deck.pptx` | 書く（唯一の書き手） | 読むだけ |
| `review_state.md` | 書かない | 書けない |
| 品質判断 | しない | する |

**判断を持つエージェントは書けず、書けるエージェントは判断を持たない。**
`review_state.md` を書くのはオーケストレータだけで、それは独自の品質判断を持たない。

評価用エージェントには**ビルダーの言い分を渡さない**。成果物だけで判断させる。

## 直列化 ─ 性能ではなく正しさの制約

* **build と fix は常に直列。** `slides/deck.pptx` は1ファイルで、python-pptx は
  パッケージ全体を読み込み、メモリ上で変更し、全体を書き戻す。
  同時実行すると**後勝ちでスライドが無言で消える**。
* **レンダリングも直列。** PowerPoint COM の `Dispatch` は起動中のインスタンスに接続するため、
  同時実行すると先に終わった方の `app.Quit()` が他方の書き出しを殺す。
* **1波のレンダリングは1回の COM セッションにまとめる。**
  `render_deck.py <deck> --slides 31-37 --png-dir <out>` は7回の起動を1回にする。
  8枚×3反復で、1枚ずつなら24回、波まとめなら3回。
* **並列化してよいのはレビューだけ。** レビュアーは PNG とテキストしか読まない。

## サブエージェントが使えない場合

`techdeck-slide-builder` / `techdeck-slide-reviewer` が利用できない環境では、
**同じループをこのターン内で実行する。**

> **よくある原因: セッション開始後にエージェント定義を作った。**
> Claude Code は `~/.claude/agents/` をセッション開始時に読み込むため、
> 追加直後のセッションでは `Agent type not found` になる。
> **新しいセッションを開始すれば使える。** 定義ファイル自体の問題ではない。
> それまでは下記のインラインモードで進めてよい。

手順・ルーブリック・反復上限・離脱条件はすべて同一。
失われるのは文脈の独立性と並列性だけであり、
**安全側の性質（`APPROVED` を出さないこと）は変わらない。**

その場合も、レビューの段では**必ず PNG を実際に読む**こと。
自分が書いたスライドであっても、`reference/review-rubric.md` に照らして機械的に採点する。

## Completion

作業完了時は、次を報告する。**下の項目だけを箇条書きで、1 項目 3 行まで。** 一覧が長いときは
`slides/reviews/batch-bNNN.md` に書いてパスを示す（報告の散文は出力と cache write の二重払いになる）。

* バッチID・対象スライド・波の構成
* スライドごとの: 反復回数 / 総合判定 / 未解決の `CRITICAL`・`HIGH` / 最終状態
* `DEFERRED` にした指摘とその理由
* `PUSHED_BACK`（技術的に誤っているとして反映しなかった指摘）と根拠
* 反復上限に達した、または発振ガードで離脱したスライドと、その未解決の対立点
* `BLOCKED` にしたスライドと理由
* `## Feedback carried forward` に追加した横断ルールと、`conventions` に吸収した規則
* 他スライドへの影響（**変更はせず報告のみ**）
* `## Approved slide change requests` に積んだ件数と一覧（既定の処理は Phase 4。
  前倒しするかはユーザーが選ぶ）
* 各スライドの字数と余裕（「数えなかったもの」を確かめた後の値）
* ユーザーに確認してほしい点 ─ **推奨案を先頭に置き、影響（再承認が要る枚数・番号の変わり方・
  字数）を添える。** この形で出した依頼は、ユーザーが毎回すぐ決められた

**報告後は停止し、ユーザーのレビューを待つ。**
エージェント自身の判断でスライドを `APPROVED` にしない。
