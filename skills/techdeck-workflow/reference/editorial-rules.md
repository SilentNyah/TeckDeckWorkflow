# AGENTS.md

## Scope

この指示は `slides/` 配下の作業に適用する。

ルートの `../AGENTS.md` と、現在のフェーズに対応する `../workflows/` 配下の指示も確認すること。

## Purpose

`slides/` では、読者が手元で閲覧し、資料単体で技術内容を理解できるPPTX資料を設計・作成する。

技術的な正確性と説明の十分性を、見栄えや簡潔さより優先する。

## Files

* `outline.md`: 資料全体の構成
* `storyboard.md`: 各スライドの詳細設計
* `speaker_notes.md`: 発表者向けの補助情報
* `review_state.md`: スライドごとの進行状態
* `reviews/`: レビュー履歴
* `deck.pptx`: 作業中のPPTX

## Content rules

* 1スライドにつき、1つの技術トピックまたは論理的なまとまりを扱う。
* 技術理解に必要な説明を、見栄えだけを理由に削除しない。
* 情報が1枚に収まらない場合は、内容を削らずスライド分割を提案する。

### 十分性は文章量ではない

「見栄えより正確性と十分性を優先する」は本プロジェクトの原則であり、変わらない。
ただし**これは「文章を減らすな」という意味ではない。**

> 同じ内容を図・表・ピクトグラムでより速く正確に伝えられるなら、
> それは**削減ではなく表現の置換**であり、十分性を一切損なわない。
> 削ってよいのは「同じ情報の重複」だけである。

**本文を書く前に、必ず一度「これは図で書けないか」を検討する。**
分量が予算を超えたときの手段は 図に置換 / ピクトグラムに置換 / スライド分割 の3つで、
**削除は手段に含まれない**（`reference/visual-design.md` §5）。

### 読者を導く

* 各スライドに**キーメッセージを1つ**置く。2行以内・簡潔な日本語・改行位置は自分で決める。
* 重要なキーワードを**文中で1〜3語**強調する。段落全体の太字は見出しであって強調ではない。
* 図・アイコン・ピクトグラムを、装飾ではなく**本文の代わり**として使う。

規定と数値は `reference/visual-design.md` が唯一の正。この節に再掲しない。
* 用語、前提条件、対象バージョン、制約、例外を必要に応じて明記する。
* speaker notesがなくても、主要な技術内容を理解できるようにする。
* 図、本文、コード、出典の内容を一致させる。

## Diagram rules

* 内容に応じて、UMLクラス図、シーケンス図、状態遷移図、アクティビティ図などを使い分ける。
* **技術スライドではUMLを積極的に使う。** UMLで表せる構造を散文や箇条書きで代用しない
  （ルーブリック `R3-9`）。
* 曖昧な概念図で、実装上重要な構造を過度に簡略化しない。
* UMLとして厳密でない図は、「概念図」または「簡略図」と明記する。
* 編集可能な図のソースを `../assets/diagrams/` に保存する。
* 図の対象範囲、読み順、省略事項を説明する。

## Code rules

* コードには、理解に必要な前後関係を含める。
* **シンタックスハイライトを必ず付ける**（`codehl.highlight()`。`R4-7`）。
* **注目行を必ず示す**（`mark_lines`。`R4-8`）。示さないコードは、
  なぜ載っているのかを読者に投げている。
* 完全版コードは `../examples/` に置く。
* スライド内コードと完全版サンプルを一致させる。
* 省略箇所はコメントなどで明示する。

## Batch creation

* Phase 3では、**既定でスライドをまとめて作成する**（既定の単位は章）。
  1枚ずつの作成は、ユーザーが明示的に求めた場合のモードである。
* 作成したスライドは、ユーザーに渡す前に **build → review → fix のループ**を通す。
  離脱条件は「未解決の `CRITICAL` / `HIGH` が 0」。手順は `workflows/phase3-batch-build.md`。
* **ループの離脱先は `AWAITING_REVIEW` であり、`APPROVED` ではない。**
  レビュー用エージェントの判定（`PASS` 等）は承認ではない。
* バッチの対象は `NOT_STARTED` のスライドのみ。`AWAITING_REVIEW` / `REVISION_REQUIRED` の
  スライドは、ユーザーの明示指示がない限り含めない。
* `slides/deck.pptx` は1ファイルのため、**ビルドとレンダリングは直列**に行う。
* 状態は `review_state.md` で管理する。書くのはオーケストレータのみ。
* エージェント自身の判断で `APPROVED` に変更しない。
* 承認済みスライドを、ユーザーの指示なしに変更しない。

## Review

スライド作成または修正後は、**必ずレンダリングして結果を見る。**

確認項目は `reference/review-rubric.md` の **§R5 表示・レンダリング** が唯一の正である。
この節に項目を再掲しない（過去に3箇所へ分裂し、内容が食い違った経緯がある）。

**PNG を見ずに済ませない。** python-pptx は PowerPoint が描画しない文字も平然と報告する。
とくに「本文が自分の枠からはみ出す」という最も頻度の高い崩れ方は、
`check_deck.py` では検出できない（`review-rubric.md` の「自動判定できないこと」を参照）。

レビュー結果を報告した後は停止し、ユーザーのフィードバックを待つ。
