# 視覚設計

スライドの**見え方**に関する唯一の基準。
`reference/review-rubric.md` の **R8** はこのファイルを参照する。
`reference/editorial-rules.md`、`workflows/phase3-*.md`、両エージェント定義も同様。

**この節の内容を他のファイルへ再掲しない。**
過去に視覚チェックリストが3箇所へ分裂し、内容が食い違った経緯がある。

---

## 0. 前提 ─ この資料には発表者がいない

読者は手元で1枚ずつ読む。だから**どこから読むかを、スライド自身が示さなければならない。**
発表者なら「ここが重要です」と言える。この資料は言えない。

## 1. 3秒ルール

> レンダリングした PNG を3秒見て、**そのスライドが言いたいこと1つ**を言えなければ、
> そのスライドは失敗している。

言えない理由は、ほぼ必ず次のどれかである。

* 一番言いたいことが、他の要素と同じ見た目で置かれている
* 一番言いたいことが長すぎて、3秒では読み終わらない
* 言いたいことが1枚に2つ以上ある（→ 分割する）

**これは好みの問題ではない。** 読者が要点を取り出せるかどうかの機能要件である。

---

## 2. 視覚重量の階段

同じスライド上の要素は、**役割ごとに明確に違う重さ**を持つ。
隣り合う段は **1.25倍以上**サイズを離す。離れていなければ階段になっていない。

| 段 | 役割 | 13.33×7.5in | 10×5.625in | 色 |
| --- | --- | --- | --- | --- |
| 1 | キーメッセージ | 22–24pt **bold** | 16–18pt **bold** | `text_bright` / `text` |
| 2 | 図・表・コード | ─ | ─ | ─ |
| 3 | カード見出し | 18–20pt bold | 14–15pt bold | `text` |
| 4 | 本文 | 12–13pt | 9–10pt | `text` |
| 5 | 注釈・凡例 | 10–11pt | 8pt | `muted` |
| 6 | 出典・参照 | 9pt | 7pt | `dim` |

段2（図）が段1（キーメッセージ）より**面積**で大きいのは正しい。
階段はサイズだけでなく、**サイズ × 色の濃さ × 位置**で作る。

値は `deck-profile.json` の `visual.size_ladder` で案件ごとに上書きできる。

---

## 3. キーメッセージ

**1スライドに1つだけ。** スライド上端に置く。

| 制約 | 既定 | プロファイルキー |
| --- | --- | --- |
| 行数 | **2行以内** | `visual.key_message_max_lines` |
| 1行の長さ | **全角30字以内** | `visual.key_message_max_chars` |
| 強調語 | **1〜3語** | `visual.emphasis_budget` |

### 改行は自分で決める

**自動折り返しに任せない。** 任せた結果が下である（実測・Slide 020）。

```text
悪い（89字を1段落で置き、PowerPoint が折り返した）
  二重派遣が発覚した場合のリスクは刑事・行政・民事の3軸に整理できる。「発覚しなけ
  れば大丈夫」ではなく、行為者個人
  ・法人（派遣元・派遣先）のそれぞれに異なる形で及ぶ。
                    ↑ 「行為者個人」と「・法人」の間で切れている
```

```text
良い（storyboard が2行を決め、builder がそれぞれを1段落として描く）
  二重派遣のリスクは【刑事・行政・民事】の3軸。
  罰則は【行為者個人にも】及ぶ。
```

storyboard の `### Key message` に**実際の改行を書く**。
builder はその行を**1行=1段落**として描く。折り返しは発生しない。

書く前に `deckkit.fits(runs, width_in)` で収まることを確認する。

### 簡潔な日本語で書く

* 主語を省かない。ただし**修飾は削る**。
* 体言止めを使ってよい。1文に主張を2つ入れない。
* 条文番号・固有名詞は削らない（正確性が先）。削るのは修飾語である。
* 「〜と考えられる」「〜という点が挙げられる」のような遠回しな述語を使わない。

## 4. 強調

### 予算は3箇所

1スライドの強調は**最大3箇所**。**強調だらけは強調なしと同じ**である。

### 見出しの太字は強調ではない

段落**全体**が太字なのは見出しやラベルであって強調ではない。
強調とは、**通常の文字の隣にあって浮き上がる span** のことである。

```python
# 見出し（強調ではない）
[R('リスクの3軸', 18, TEXT, CJK, b=True)]

# 強調（これが読者の目を導く）
[R('罰則は', 22, TEXT, CJK, b=True),
 R('行為者個人にも', 22, RED, CJK, b=True, hl='FFF0A8'),
 R('及ぶ。', 22, TEXT, CJK, b=True)]
```

`check_deck.py --profile` はこの2つを区別して報告する。

### 手段

| 手段 | 使いどころ |
| --- | --- |
| 色（`accent_*`） | 意味を持つ強調。**プロファイルの `conventions` に従う** |
| 太字 | 色と併用。単独では弱い |
| ハイライト `hl=` | 1スライド1箇所まで。最も強い。使いすぎると下品になる |
| サイズ | 段を1つ上げる。文中では使わない |

**色だけで意味を表さない。** 色覚特性・白黒印刷で消える。
必ず語・記号・位置のいずれかを併用する（`R1` の観点ではなくアクセシビリティの要件）。

### 色の意味は案件が決める

`deck-profile.json` の `conventions` が正。
たとえば本デッキでは 適法=`accent_green` / 違法=`accent_red` / 寄与要因=`accent_pink` /
中立の注記=`accent_purple`。**意味を持つ色を、意味と無関係な装飾に流用しない。**

## 5. 文章量の予算

| 予算 | 既定 | プロファイルキー |
| --- | --- | --- |
| 1スライドの総文字数 | **450字** | `visual.body_char_budget` |

超えたときに取れる手段は**3つだけ**である。

1. **図に置き換える**（関係・順序・分類・比較は、文章より図が速い）
2. **ピクトグラムに置き換える**（列挙・カテゴリ）
3. **スライドを分割する**

> **削除は手段に含まれない。**
> 技術的な説明を、量が多いという理由だけで削らない。
> これは `editorial-rules.md` の「見栄えより正確性と十分性」と矛盾しない ─
> **置換は削減ではない。**

「本文を書く前に、これは図で書けないかを一度検討する」。これを毎回行う。

## 6. 図・アイコン・ピクトグラム

### 図を選ぶ

構造には UML を使う。曖昧な概念図で実装上重要な構造を潰さない。
種類の選び方と記法の要件は `editorial-rules.md` の Diagram rules と rubric `R3`。

技術スライドでは、**UMLで表せる内容を散文や箇条書きで代用しない**（`R3-9`）。

| 表したいもの | 図 |
| --- | --- |
| 静的な構造・関係 | クラス図 / コンポーネント図 |
| 時間順のやりとり | シーケンス図 |
| 状態と遷移 | 状態遷移図 |
| 手順・分岐 | アクティビティ図 |
| 比較・対応 | 比較表 |
| 量・割合 | グラフ |

### ピクトグラム

`pptx-toolkit/scripts/pictogram.py` に33種。パレット色で描かれるので必ず馴染む。

**使ってよい場面**

* 列挙項目の識別子（各項目に1つ）
* 状態・判定の視覚化（`check` / `cross` / `warning` / `prohibited`）
* 登場人物・組織・成果物（`person` / `people` / `building` / `document`）

**使ってはいけない場面**

* 装飾。情報を持たないアイコンは**ノイズであって余白ではない**
* 1スライドに7個以上。識別子として機能しなくなる
* 意味が一意に伝わらないもの（迷ったら語で書く）

### 図と本文の一致

図・本文・コード・出典の内容は必ず一致させる（`R3-4` `R3-5`）。
図を直したら本文も直す。**片方だけ直す修正が最も多い回帰である。**

## 7. コード

技術スライドのコード断片には**必ずシンタックスハイライトを付ける**（`R4-7`）。
`codehl.highlight()` / `codehl.code_block()` がプロファイルの `code_palette` を適用する。

**注目箇所を必ず示す**（`R4-8`）。

```python
code_block(s, x, y, w, h, src, 'kotlin', PROF,
           line_numbers=True, mark_lines=[12, 13],
           mark_hl=PAL['highlight'], focus=True)
```

`focus=True` は注目行以外を**不透明度で後ろに下げる**だけで、色は `code_palette`
のまま残る（深さは `dim_alpha`、既定 0.55）。
**注目行以外を一色の灰色に塗りつぶさない。** 20 行中 2 行しか注目行がない
断片では、それはハイライトの無い灰色の壁であり、`R4-7` 違反になる。
`mark_hl` にはプロファイルの `palette.highlight` を渡す。

`mark_lines` の無いコード断片は、**なぜそれが載っているのかを読者に投げている。**

未対応の言語は色を付けない。**誤ったハイライトは、無いより悪い**
（コードに無い構造を主張してしまう）。

---

## 8. 余白

* スライド外周のマージンを本文が侵さない
* カードとカードの間隔は、カード内の行間より**明確に広い**
* 埋まっていない領域を、埋めるためだけの要素で埋めない

**余白は削れる無駄ではなく、階段を成立させている要素である。**

| --- | --- | --- |
