# レビュー・ルーブリック

スライドを評価するときの**唯一の基準**。
`templates/review-report.md`、`reference/editorial-rules.md`、
`workflows/phase3-pptx-comment-review.md` はすべてこのファイルを指す
（過去に視覚チェックリストが3箇所へ分裂し、項目が食い違った経緯がある）。

**R8 の実体は `reference/visual-design.md` にある。** 数値（行数・字数・強調数・
文字数予算）はすべてそちらが正で、ここには再掲しない。

各項目には安定したIDを付けてある。指摘は必ず `Rubric: R1-A-2` の形で項目を引用する。
**根拠として引ける項目が無い指摘は、指摘ではない。**

## 判定・重要度・分類

* 総合判定（レビュー判定・名前空間(3)）: `PASS` / `PASS_WITH_MINOR_FIXES` /
  `REVISION_REQUIRED` / `BLOCKED` / `AWAITING_USER_REVIEW`
* 重要度: `CRITICAL` / `HIGH` / `MEDIUM` / `LOW`
* 分類タグ: `[TECH]` `[EXPLAIN]` `[DIAGRAM]` `[CODE]` `[SOURCE]` `[CONSISTENCY]` `[LAYOUT]` `[VISUAL]`
  `[LAYOUT]` は「壊れている」（R5）、`[VISUAL]` は「優先順位が伝わらない」（R8）。別物である。

定義は `reference/status-vocabulary.md` が正。

**合格バー: 未解決の `CRITICAL` / `HIGH` が 0。**
これは `workflows/phase4-deck-final-review.md` の最終化基準と同一のバーである。
**このバーを満たしたスライドの終端は `AWAITING_REVIEW` であって `APPROVED` ではない。**
`APPROVED` はユーザーの明示的な指示によってのみ設定される。

## R2 説明の十分性

* `R2-1` スライド本文だけで主要内容を理解できる
* `R2-2` 主語や対象が明確である
* `R2-3` 因果関係が説明されている
* `R2-4` 言葉足らずな説明がない
* `R2-5` 箇条書きだけで意味が曖昧になっていない
* `R2-6` 簡略化によって誤解が生じない

> R2 はこの資料の存在意義そのものである。読者は手元で読み、発表者はいない。
> **スライドから読み取れなければ、スライドが誤っている。**

## R4 コード

* `R4-1` コードが技術的に正しい
* `R4-2` 対象バージョンで利用できる
* `R4-3` 完全版サンプルと一致している（`examples/`）
* `R4-4` 必要な文脈がある

* `R4-6` 注目箇所が明確である
* `R4-7` シンタックスハイライトが適用され、`code_palette` に従っている
  （`codehl.highlight()`。未対応言語で色を付けていないのは**適合**である）

## R5 表示・レンダリング

**PNG を見なければ判定できない項目である。** XML からは分からない。

* `R5-1` テキストのはみ出しがない
* `R5-2` 図形や文字の重なりがない
* `R5-3` 図中の文字が判読できる
* `R5-4` コードが途中で切れていない
* `R5-5` 表が崩れていない
* `R5-6` フォント置換や文字化けがない
* `R5-7` 出典が読める
* `R5-8` 読み順が明確である
* `R5-9` 矢印や関連線が意図した図形に接続している
* `R5-10` PPTX と PDF／PNG で表示差がない
* `R5-11` 矢印の**向き**が、ラベル・本文・storyboard が示す動作の方向と一致している

`R5-9` は `editorial-rules.md` の「矢印や関連線の接続」と
`phase3-pptx-comment-review.md` の「UML図の線や矢印」を統合したもの。
接続先の正しさ（どの図形に刺さっているか）と記法の正しさの両方を見る。

`R5-11` は `R5-9` と**別項目である**。正しい図形同士が線で結ばれていても、
**矢じりだけが逆を向いている**という壊れ方が実在する（実例: 概念図で
「B社がC社に労働者を供給する」と書いた図の矢じりが、C社→B社 を指していた）。
矢印を**1本ずつ**、根元がどの図形で先端がどの図形かを PNG で確かめ、
ラベルの動作主体（誰が誰に対して行うか）と突き合わせること。
矢印が1本でも逆なら、図は本文と逆のことを言っているので `HIGH` 以上。

結果としての向きだけを見ること。**どの関数で描いたかは適合の根拠にならない。**
`deckkit.arrow(s, x1, y1, x2, y2)` は「指定した終点 `(x2, y2)` に矢じりを出す」
ことしか保証しないので、**終点の選び方自体が storyboard と逆**なら誤りは残る。

## R6 スライド間の整合

**`MODE: batch` のときだけ使う。** 個別スライドのレビューでは判定しない。

* `R6-1` 用語が `notes/glossary.md` と全スライドで一致している
* `R6-2` 記法（コードフォント・強調・箇条書きの粒度）が一致している
* `R6-3` 同じ役割の要素に同じ配色を使っている（`deck-profile.json` の規約に従う）
* `R6-4` 「詳細は Slide NN」等の前後参照が実在し、番号が正しい
* `R6-5` 同じ説明が複数スライドで重複していない
* `R6-6` 説明順に飛びがない（前提が後から出てこない）
* `R6-7` `## Feedback carried forward` のルールが全スライドで守られている
* `R6-8` キーメッセージの体裁（位置・サイズ・行数・強調の付け方）が全スライドで一致している
  （`visual-design.md` §2〜§4。1枚ずつ作ると最も揺れる箇所）

`R6-4` は特に壊れやすい。スライドの削除・番号の繰り上げで参照が腐る。

## R7 自動判定（`check_deck.py`）

```text
python <pptx-toolkit>/scripts/check_deck.py <deck.pptx> --profile <profile.json> --slide <N>
```

* `R7-1` `<p:nvGrpSpPr>` の欠落・位置（`CRITICAL` ─ PowerPoint がファイルを開けなくなる）
* `R7-2` `<a:endParaRPr>` が段落の最後でない（`CRITICAL` ─ 段落が空白で描画される）
* `R7-3` shape id の重複（`HIGH`）
* `R7-4` 背景が slide/layout/master のどこにも無い（`HIGH` ─ 白地に白文字になる）
* `R7-5` 図形がキャンバス外（`MEDIUM`）
* `R7-6` パレット外の色・プロファイル外のフォント（`LOW`）
* `R7-7` 自分の枠からはみ出しそうな段落（`MEDIUM` ─ **推定**。`R5-1` の前段フィルタ）
* `R7-8` 文中強調が0、または過多（`LOW` ─ `R8-4` / `R8-5` の前段フィルタ）
* `R7-9` 文字数が `visual.body_char_budget` 超過（`LOW` ─ `R8-7` の前段フィルタ）

`R7-7`〜`R7-9` は `--profile` を渡したときだけ動く推定であり、`--no-visual` で切れる。
**推定なので `R5-1` / `R8-4` / `R8-7` の判定を代行しない。**
0件でも PNG を見る義務は変わらない。

### 終了コードの罠

`check_deck.py` は **`CRITICAL` / `HIGH` のときだけ 1 を返す。**
キャンバス外（`MEDIUM`）とコントラスト不足（`MEDIUM`）だらけのデッキでも **0 で終わる。**
**必ず出力行を読むこと。** `--json` は存在しない。書式は `  [SEVERITY] where message`。

`--contrast` は指示された場合を除き**使わない**。
成熟したデッキでは正当なバッジを多数（実測26件）誤検出する。

## R8 視覚的強調・情報設計

**PNG のみで判定する。** 規定の実体は `reference/visual-design.md`。
このルーブリックが存在する前、視覚的な優先順位を指摘する根拠が1つも無く、
「好みの問題は指摘しない」規律のもとでレビュアーは**構造的にメリハリ不足を指摘できなかった。**
R8 はその穴を塞ぐためにある。

| ID | 項目 | 既定の重要度 |
| --- | --- | --- |
| `R8-1` | 3秒でキーメッセージが1つに特定できる | **`HIGH`** |
| `R8-2` | キーメッセージが2行以内で、改行が文節境界にある | `MEDIUM` |
| `R8-3` | キーメッセージが本文より明確に強い（サイズ・色・位置） | `MEDIUM` |
| `R8-4` | 重要キーワードが文中で1〜3語強調されている | `MEDIUM` |
| `R8-5` | 強調が過剰でない | `MEDIUM` |
| `R8-6` | 色の使い方が `deck-profile.json` の `conventions` と一致している | `MEDIUM` |
| `R8-7` | 文字数が予算内、または図・ピクトグラムに置換されている | **`HIGH`** |
| `R8-8` | 図・アイコンが装飾でなく情報を担っている | `MEDIUM` |
| `R8-9` | 余白があり、詰め込まれていない | `LOW` |

### 重要度を上げてよい条件と、上げてはいけない理由

**`HIGH` は `R8-1` と `R8-7` だけである。** この2つだけがループのゲートになる。

* `R8-1` が落ちているスライドは、読者が要点を取り出せない。この資料の存在意義に反する。
* `R8-7` が落ちているスライドは、`R8-1`〜`R8-5` を個別に直しても改善しない。
  **分量そのものが原因**なので、置換か分割が要る。

**残りを `HIGH` に格上げしない。** R8 は本質的に程度問題を含むため、
全部をゲートにするとループが反復上限まで空回りし、ユーザーの時間を奪う
（「指摘の規律」5 と同じ理由）。`MEDIUM` は報告され、`DEFERRED` になり、
ユーザーが判断する ─ それで十分機能する。

### `R8-1` の判定手順

**storyboard を読む前に**、PNG を3秒見て、持ち帰った1点を書き出す。

* 1点を書けた → `R8-1` 適合。その1点を storyboard の `### Key message` と照合する
  （食い違えば `R8-3` か `R2`）
* 書けなかった、または2点以上挙がった → `R8-1` 不適合。**これが証拠である**

自分が読み取れなかったという事実は、好みではない。読者も読み取れない。

### `R8-7` を指摘するときは手段まで書く

`Recommended action` に、`visual-design.md` §5 の3手段のどれかを名指しする。

1. 図に置き換える（どの内容を、どの図種で）
2. ピクトグラムに置き換える（どの列挙を）
3. スライドを分割する（どこで切るか）

**「減らす」は推奨アクションとして無効である。**
説明を削れという指摘は `editorial-rules.md` に反する。

## 自動判定できないこと（必読）

`check_deck.py` が判定できるのは **R7 の6項目、すなわち構造だけ**である。

* **R1〜R4 の36項目は 0 件が機械判定可能。** 技術的正確性・説明の十分性・図・コードは、
  レンダリング結果を読んで判断するしかない。
* **R8 の9項目のうち、機械が触れるのは分量と強調の「数」だけである**（`R7-7`〜`R7-9`）。
  優先順位が読者に伝わるか（`R8-1` `R8-3` `R8-8`）は PNG を見る以外に判定できない。
* **テキストが「自分の図形」からはみ出す事象は検出されない**（`R5-1`）。
  検出されるのは「図形がキャンバス外」（`R7-5`）だけである。本文が多すぎて枠から溢れる
  という最も頻度の高い崩れ方は、**PNG を見る以外に見つける方法がない。**
* **図形どうしの重なり判定は存在しない**（`R5-2`）。
* **矢印の向きは検出できない**（`R5-11`）。線は引かれ、図形にも接続され、
  `check_deck.py` も通る。図が本文と逆のことを言っているだけなので、
  **PNG の矢印を1本ずつ読む以外に見つける方法がない。**
* 表の崩れ・文字化け・コードの途切れも、すべて PNG のみ。

> **R7 が通ったことは R1〜R4・R8 について何も意味しない。必ず PNG を見ること。**

## 指摘の規律

ループを収束させるための制約。指摘を出す側が守る。

1. **根拠を引く。** ルーブリック項目ID、storyboard の行、`SRC-NNN`、
   PNG 上の具体的な位置のいずれかを必ず示す。
2. **要求を発明しない。** ルーブリック、storyboard、`deck-profile.json`、
   `notes/glossary.md` が仕様の全体である。**好みの問題は指摘しない。**
3. **蒸し返さない。** 反復2回目以降は、前回の指摘それぞれについて
   「新しい PNG で解消を確認した」か「まだ解消していない具体的理由」を述べる。
   根拠付きで反論された指摘を、同じ内容で再提出しない。
4. **最終反復では新規の `MEDIUM` / `LOW` を出さない。**
   その時点で意味があるのは回帰と未解決の `CRITICAL` / `HIGH` だけである。
5. **重要度を盛らない。** `CRITICAL` は「このままでは出せない」であって
   「好きではない」ではない。盛るとループが上限まで空回りし、ユーザーの時間を奪う。

## 指摘できる相手

ルーブリックに照らして storyboard 自体が誤っている・不足している場合は、**そう指摘する。**
その指摘はスライド作成側では直せない（`Fixable by builder: no`）。
技術的に誤ったフィードバックをそのまま反映しないという原則は、
人間のレビュアーにも評価用エージェントにも等しく適用される。
